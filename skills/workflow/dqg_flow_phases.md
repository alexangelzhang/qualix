# DQG 全流程工作流定义

## 流程总览

```
┌─────────────────────────────────────────────────────────────┐
│  Phase Q01: 需求结构化                                         │
│  输入: PRD/飞书文档                                           │
│  产出: REQ/BR/SE + GAP + OPEN                                │
│  放行: 结构化率 100%, SE 显式化 100%                            │
└──────────────────────┬──────────────────────────────────────┘
                       │
          ┌────────────┼────────────┬──────────┐
          ▼            ▼            ▼          ▼
┌──────────────┐ ┌──────────────┐ ┌────┐ ┌────┐
│ Phase Q04    │ │ Phase Q03    │ │Q05 │ │Q07 │
│ 覆盖度审计    │ │ 质量评审      │ │    │ │    │
│ (可并行)     │ │ (可并行)      │ │    │ │    │
└──────────────┘ └──────────────┘ └─┬──┘ └────┘
                                    ▼
                               ┌────────┐
                               │ Phase Q06 │
                               │ 单测审计  │
                               └────────┘
```

## Phase 生命周期

每个 Phase 遵循统一的生命周期：

```
[收集输入] → [execute] → [加载上下文+Skill] → [执行任务] → [产出交付物]
    → [finalize(校验)] → [展示确认清单] → [approve/skip/修改]
```

## Phase Q01: 需求结构化

### 前置条件
- 无（流程起点）

### 输入收集
| 输入 | 必填 | 说明 |
|------|------|------|
| PRD/飞书链接 | 是 | 飞书链接自动调 feishu_direct_ingest.py |
| 补充图片目录 | 否 | 有图片时提示是否做语义解析 |

### 执行动作
1. 飞书文档 ingest（自动）
2. 可选图片语义解析
3. 按 skill 逐步执行：REQ/BR 提取 → SE 显式化 → GAP/OPEN 梳理 → 完整性 Gate

### 产物校验
- `phase_a_report.md` 存在且非空
- `phase_a_structured.json` 通过 Pydantic schema 校验
- 至少 1 个 REQ 级需求

### 放行条件
- REQ/BR 结构化率 = 100%
- SE 显式化率 = 100%
- 所有冲突语义已进入 OPEN
- 所有缺失口径已进入 GAP
- 未输出 UT/EUT

### 放行后解锁
- Phase Q04, Q03, Q05, Q06, Q07

---

## Phase Q04: 技术方案覆盖度审计

### 前置条件
- Phase Q01 approved

### 输入收集
| 输入 | 必填 | 说明 |
|------|------|------|
| 技术方案文档 | 是 | 飞书链接或本地路径，多份用逗号分隔 |
| 代码仓库(master) | 否 | 扫描已有实现和 TMF 链路 |
| 知识库 | 否 | 飞书链接或本地路径 |

### 执行动作
1. 范围确认（Scope Challenge）
2. 可选：master 分支已有实现扫描
3. REQ 级覆盖扫描 → BR 级覆盖详查 → SE 覆盖审计
4. GAP/OPEN 闭环检查
5. 反向审计（NEW_DESIGN + NOT_IN_SCOPE）

### 产物校验
- `tech_design_coverage_review.md` 存在
- 跨 Phase ID 引用完整（Q04 引用的 REQ/SE/GAP 在 Phase Q01 中存在）

### 放行条件
- REQ 覆盖率 = 100%（含 IMPLICIT 须附依据）
- SE 覆盖率 >= 90%
- GAP 闭环率 >= 60%
- 无 P0 未闭环风险

### 可与 Q03 并行

---

## Phase Q03: 技术方案质量评审

### 前置条件
- Phase Q01 approved

### 输入收集
| 输入 | 必填 | 说明 |
|------|------|------|
| 技术方案文档 | 是 | 可复用 Q04 的 |
| 代码仓库(feature) | 否 | 追踪改动功能点的完整 TMF 链路 |
| feature 分支名 | 否 | 要分析的分支 |

### 执行动作
1. 范围确认 + feature 分支全链路梳理
2. 逐维度交互式评审：架构 → 接口 → 数据 → 异常 → 性能
3. Failure Mode 分析
4. 保护点汇总（幂等/并发/状态/事务在哪层实现）

### 产物校验
- `tech_design_quality_review.md` 存在
- 含调用链路图（CALL_CHAIN 章节）

### 放行条件
- 无 CRITICAL_GAP
- 架构分层无 FAIL 项
- P0 问题已有修复方案

### 可与 Q04 并行

---

## Phase Q05: 单测生成

### 前置条件
- Phase Q01 approved

### 输入收集
| 输入 | 必填 | 说明 |
|------|------|------|
| 代码仓库 | 是 | 本地路径，多个用逗号分隔 |
| 目标模块 | 是 | 要生成单测的模块/类路径 |

### 执行动作
1. 读取 Phase Q01 的 REQ/BR/SE 作为测试需求
2. 读取代码结构，识别 TMF 链路
3. 生成 EUT 矩阵
4. 生成单测代码到 temp/ 目录（不影响现有代码）
5. Step 层使用 MockedStatic<TMF> 模式（禁止空洞 assertThrows）

### 产物校验
- `eut_matrix.md` 存在
- temp/ 目录下有 *DqgTest.java 文件
- 每个测试有 @DisplayName 标注需求 ID

### 放行条件
- EUT 矩阵覆盖所有 REQ/BR/SE
- 单测使用强断言
- 异常路径有对应测试

### 特殊规则
- 测试写入 temp/ 目录，不提交仓库
- 用于 AB 对比，不替换现有测试

## Phase Q06: 单测覆盖审计

### 前置条件
- Phase Q01 approved

### 输入收集
| 输入 | 必填 | 说明 |
|------|------|------|
| 代码仓库(含单测) | 是 | 包含 src/test 的仓库 |
| 覆盖率报告 | 否 | JaCoCo 报告路径 |

### 执行动作
1. 按模块分别审计（每个模块独立章节）
2. 按 DDD 层统计测试文件（extension/step/ability/cmdexe/provider/infra）
3. 抽样读取测试文件，评估质量（强/中/弱）
4. 检查空洞测试（assertThrows(Throwable.class)）
5. 需求覆盖矩阵（REQ → 测试映射）
6. GAP 覆盖评估（幂等/并发测试）
7. 如有 temp/DqgTest，做 AB 对比

### 产物校验
- `ut_audit_report.md` 存在
- 按模块分章节

### 放行条件
- T1 核心异常分支有覆盖
- 无 WRONG_TARGET 问题
- 结论：PASS / PASS_WITH_RISKS / FAIL

---

## Phase Q07: 代码评审

### 前置条件
- Phase Q01 approved

### 输入收集
| 输入 | 必填 | 说明 |
|------|------|------|
| 代码仓库 | 是 | 本地路径 |
| 评审分支 | 是 | feature 分支名 |
| 基线分支 | 否 | 默认 master |

### 执行动作
1. 按模块分别评审
2. 每个模块先梳理完整 TMF 调用链路（CALL_CHAIN）
3. 在链路上下文中执行评审 checklist
4. 保护点验证（幂等/并发/状态/事务在哪层）
5. 多入口检查（同一 Ability 的不同调用入口是否都有保护）
6. REQ → CODE 覆盖缺口

### 产物校验
- `review_report.md` 存在
- 含调用链路图
- 每条发现标注链路位置

### 放行条件
- 无 BLOCKER 级问题
- REQ/BR/SEM → CODE/TEST 覆盖缺口已确认
- 结论：DONE / DONE_WITH_CONCERNS / BLOCKED

### 特殊规则
- 禁止孤立评审（必须在链路上下文中判断）
- 禁止自动修改代码
