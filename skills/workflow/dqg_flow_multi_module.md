# DQG 多模块工作流

## 适用场景

当一个项目涉及多个代码仓库或多个业务模块时（如权益退款 + 权益查询 + 权益下发），使用多模块工作流。

## 模块识别

### 时机
Phase A 完成后，根据 REQ 的功能边界和代码仓库的对应关系，识别模块：

```
Phase A 产出的 REQ 列表
    ↓
按功能边界分组
    ↓
每组对应一个或多个代码仓库
    ↓
形成模块清单
```

### 模块定义

每个模块包含：
- 模块名称（如"权益退款"）
- 关联的 REQ/BR/SE 列表
- 代码仓库路径（center + admin）
- feature 分支名
- 负责人（可选）

### 示例

```json
{
  "modules": {
    "权益退款": {
      "reqs": ["REQ-001", "BR-101", "BR-102"],
      "code_repo": ["car-equity-center", "car-equity-admin"],
      "feature_branch": "feature_main_20260309_refund"
    },
    "权益查询": {
      "reqs": ["REQ-002", "REQ-003", "BR-201", "BR-301"],
      "code_repo": ["query/car-equity-center", "query/car-equity-admin"],
      "feature_branch": "feature_main_20260203_equity_move"
    }
  }
}
```

## 执行策略

### Phase A / A.5: 整体执行
- Phase A 对整个 PRD 做需求结构化，不按模块拆分
- Phase A.5 对整体技术方案做覆盖度审计

### Phase A.6 / B / C / D: 按模块执行

每个 Phase 内部按模块分别执行，产出按模块分章节的报告：

```
Phase A.6:
  ├── 模块1: 权益退款 — 链路追踪 + 质量评审
  └── 模块2: 权益查询 — 链路追踪 + 质量评审

Phase B:
  ├── 模块1: 权益退款 — temp/ 目录生成单测
  └── 模块2: 权益查询 — temp/ 目录生成单测

Phase C:
  ├── 模块1: 权益退款 — 测试审计
  └── 模块2: 权益查询 — 测试审计

Phase D:
  ├── 模块1: 权益退款 — 链路级代码评审
  └── 模块2: 权益查询 — 链路级代码评审
```

### 并行策略

- 同一 Phase 内的多个模块可以并行（派发多个 agent）
- 不同 Phase 之间按依赖关系执行
- A.5 和 A.6 可以并行
- B/C/D 可以并行（都只依赖 A）

```
Phase A (整体)
    ↓
Phase A.5 (整体) ∥ Phase A.6 (按模块并行)
    ↓
Phase B (按模块并行) ∥ Phase C (按模块并行) ∥ Phase D (按模块并行)
```

## 报告汇总

每个 Phase 的报告按模块分章节，最后有汇总：

```markdown
# Phase D 代码评审报告

## 模块1: 权益退款
### 调用链路图
### 发现清单
### 结论

## 模块2: 权益查询
### 调用链路图
### 发现清单
### 结论

## 汇总
| 模块 | CRITICAL | MAJOR | MINOR | 结论 |
|------|----------|-------|-------|------|
| 权益退款 | 0 | 4 | 2 | DONE_WITH_CONCERNS |
| 权益查询 | 0 | 1 | 0 | DONE |
```

## 跨模块检查

多模块场景下需额外检查：
1. **接口契约一致性** — 模块间的 Dubbo/HTTP 接口入参出参是否一致
2. **枚举值一致性** — 跨模块共享的枚举（如状态枚举）是否定义一致
3. **数据流转完整性** — 模块 A 产出的数据是否被模块 B 正确消费
4. **事务边界** — 跨模块操作的事务保障（最终一致性/补偿机制）
