# 资金安全识别框架

用于把“资金安全审计”拆成可重复执行的步骤。顺序不要颠倒。

## 1. 资产识别

先识别代码实际操作的资产，不要把所有金额字段都等同于资金。

常见资产类型：
- 余额、可用余额、冻结余额
- 实付金额、退款金额、提现金额、手续费、结算金额
- 优惠券、积分、库存权益、授信额度、可提现额度

代码信号：
- `amount`、`refundAmount`、`fee`、`balance`、`frozenAmount`
- 券表、积分账户、额度表、流水表、分录表、结算单

必问问题：
- 这个字段代表“记账事实”还是“展示字段”
- 资产的最终记账点在哪里
- 是否同时存在主账、分账、渠道账

## 2. 资产流转路径

画出资产从哪里到哪里。

常见路径：
- 用户 -> 平台 -> 商户
- 平台 -> 用户
- 可用余额 -> 冻结余额 -> 可用余额
- 权益池 -> 用户账户 -> 核销记录

必问问题：
- 谁发起
- 谁审批
- 谁记账
- 谁通知下游
- 谁补偿

如果无法描述完整流转，就不能判断丢失点和止损点。

## 3. 触发者与入口

同一条资金逻辑，入口不同，风险级别会不同。

重点入口：
- 用户请求
- 第三方回调
- 内部 RPC
- MQ 消费
- 定时任务
- 管理后台操作

高风险入口特征：
- 会自动重试
- 会被重复投递
- 能被低权限角色触发
- 信任外部字段

## 4. 业务不变量

先写不变量，再去找破坏它们的代码。

默认不变量模板：
- 同一业务单最多成功一次
- 退款累计不得超过实付
- 提现不得超过可用余额
- 可用、冻结、总额之间必须守恒
- 只有合法状态迁移才能触发资金动作
- 外部回调只能确认事实，不能直接定义金额和状态

高危判定规则：
- 只要代码可能破坏核心不变量，优先按高危分析

## 5. 重复执行与幂等

资金损失最常见来源之一。

重点检查：
- 是否存在幂等键
- 是否有数据库唯一索引
- 是否有去重记录表
- 是否有消费记录或补偿记录
- 是否只做了“查询后再处理”的弱幂等

危险信号：
- “先查不存在，再插入/执行”
- 幂等只靠缓存，不落库
- MQ 消费先执行业务，再记处理状态
- 补偿任务根据失败状态反复扫描，但没有业务唯一键

## 6. 并发与原子性

重点找 check-then-act 和读改写模式。

危险模式：
- `if (balance >= amount) { balance -= amount }`
- 先查累计退款，再单独更新退款金额
- 多张表跨事务更新
- 锁只保护内存，不保护数据库状态
- 先更新本地，再异步推下游，没有幂等回执校验

必问问题：
- 两个请求同时打进来会怎样
- 是否存在事务外读写
- 是否有条件更新、乐观锁、悲观锁
- 是否依赖分布式锁，锁粒度是否正确

## 7. 状态机与流程绕过

资金错误经常不是算错，而是状态被绕过。

重点看：
- 未支付订单是否可退款
- 已结算单据是否还能重复结算
- 已关闭订单是否可重新履约
- 未审批是否可直接出金
- 失败状态是否会触发错误补偿

危险信号：
- 只校验“当前状态不为空”
- 允许任意状态覆盖
- 状态迁移规则散落在多个方法中

## 8. 金额精度与边界

很多资损不是攻击，而是边界和精度错误。

重点检查：
- 负数金额、零金额、超大金额
- 元/分混淆
- 币种混用
- `BigDecimal(double)`
- `equals` 和 `compareTo` 混用
- 舍入方向不一致
- 手续费、费率、折扣、税费上下限未校验

## 9. 信任边界与权限

重点看系统是否过度信任外部或内部调用方。

检查项：
- 回调验签
- 来源校验
- 租户隔离
- 订单归属校验
- 角色权限
- 审批链路
- 后台操作二次确认

危险模式：
- 直接信任客户端传入的金额、状态、商户 ID
- 内部 RPC 默认可信，不做二次校验
- 管理后台只校验角色，不校验资源归属和审批状态

## 10. 补偿、对账、告警、止损

即使代码有缺陷，也要判断系统是否有二道防线。

重点检查：
- 是否有对账
- 对账频率是否足够
- 是否有差异告警
- 是否有熔断/冻结能力
- 是否有修复工具和审计日志
- 补偿是否可重复执行，是否带唯一业务键

治理缺口不是“次要问题”。在资金场景里，治理缺口本身就可能是高风险。

## 最终判断规则

一条问题至少满足以下之一，才应进入正式风险清单：
- 会直接造成真实资金或资产损失
- 会在高概率场景下造成超额退款、重复出款、重复发放
- 会导致长期账实不符且缺少及时发现与止损手段
- 可被低成本套利

如果只是“实现看起来不优雅”，不要硬报成资损风险。
