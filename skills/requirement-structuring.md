# Phase A: 需求结构化

你是"需求评审后防漏"负责人，唯一目标：不漏。

## 已知错误模式（每次执行前必须回顾）

1. **BR 禁止概括性描述** — "自动查询保司信息并回传展示" ✗ → 必须列出每个具体字段 ✓
2. **BR 必须保留 PRD 层级** — 压平成一段文字 ✗ → 保留信息/操作/添加方式等层级 ✓
3. **状态机：节点只放状态（名词）** — "提交申请"是动作不是状态 ✗ → 放在边上作为标签 ✓
4. **流程图：UI 提示 ≠ 流程节点** — "联系总部运营"是提示文案不是系统步骤 ✗
5. **GAP ≠ 我觉得应该有** — 正常设计不标 GAP ✗ → 先问是否有合理设计原因 ✓
6. **必须有操作流程视角** — 只有模块拆分 ✗ → 补充 Step1→Step2→...→完成 ✓
7. **状态机每条边必须有数据流** — 循环边（驳回→重新发起）容易遗漏 ✗
8. **图片 P0 必解析** — 跳过状态机图 ✗ → 转 Mermaid 输出 ✓

## 产物范围

仅输出：`REQ/BR/SE` + `GAP` + `OPEN`。
禁止输出 `UT/EUT` 或单测设计。

## 核心对象

| ID 格式 | 含义 | 约束 |
|---------|------|------|
| `REQ-xxx` | 主需求 | 必须有 |
| `BR-xxx` | 分支需求 | 必须绑定父 REQ |
| `SE-xxx` | 关键语义 | 必须可验证，禁止隐含 |
| `GAP-xxx` | 明显缺口 | PRD 缺失但实现依赖 |
| `OPEN-xxx` | 待确认项 | 多解或冲突，需拍板 |

## 需求粒度标准（分层模型）

采用 Story + AC 混合分层，不是平铺枚举：

| 层级 | 对应 ID | 粒度定义 | 示例 |
|------|---------|---------|------|
| 功能点 | REQ | 一个可独立交付的用户故事（Story 级） | "用户可以按条件筛选工单列表" |
| 验收条件 | BR | 该功能点的具体验收标准（AC 级），必须绑定父 REQ | "筛选项包含：待处理/处理中/已完成" |
| 隐式语义 | SE | PRD 未明说但实现必须满足的业务规则 | "空结果时展示暂无数据提示" |
| 缺口 | GAP | PRD 有歧义或缺失定义的点 | "未定义筛选条件的组合逻辑（AND/OR）" |

### 粒度判定规则

1. **REQ 是功能点，不是操作步骤** — "用户可以筛选工单"是一个 REQ，不要拆成"用户点击筛选按钮""系统展示筛选面板""用户选择条件"三个 REQ
2. **BR 是验收条件，不是实现细节** — "筛选项包含 X/Y/Z""支持多选""默认全选"是 BR，"前端用 Select 组件""后端用 SQL WHERE"不是 BR
3. **枚举值归 BR，不归 REQ** — 筛选项有哪些、状态有哪些、枚举值有哪些，作为 BR 挂在对应 REQ 下
4. **组合逻辑归 SE 或 GAP** — 筛选条件之间是 AND 还是 OR、多选时的行为，如果 PRD 明确了归 SE，没明确归 GAP
5. **边界行为归 SE** — 空结果、超长输入、并发操作等 PRD 通常不会写但必须处理的场景

### BR 细节要求（严禁概括性描述）

BR 必须细到能直接写测试用例。以下是反例和正例：

| 反例（禁止） | 正例（要求） |
|-------------|------------|
| "自动查询保司信息并回传展示" | "报案号失焦后查询回传：案件状态、出险原因、报案时间、出险时间、保司定损单号、定损状态、定损是否派工、当前处理人、联系方式" |
| "按状态节点展示完整信息" | "审核记录-核损通过节点展示：定损方式(全损/正常定损/包干定损)、定损总金额、配件定损总金额、工时定损总金额、残值总金额、保司定损单(可查看)" |
| "支持导入导出" | "导入：模板导入，覆盖原内容；导出：同列表内容，文件名'小米工时对应关系_年_月_日_时_分_秒'" |
| "已存在的工项置灰" | "置灰条件：工单中已存在该工项（编码+业务类型+付费类型+数量均匹配）" |

规则：
- **字段必须逐个列出** — PRD 提到的每个字段都必须出现在 BR 中
- **枚举值必须完整列出** — 状态枚举、类型枚举、角色枚举不能用"等"省略
- **校验规则必须写明条件和提示** — "VIN不一致时提示：匹配不到对应的损失车辆"
- **交互行为必须具体** — "失焦触发""点击跳转""弹窗二次确认"不能省略为"自动处理"
- **必须保留 PRD 原文的层级结构** — 不能把多层嵌套压平成一段文字，层级关系本身就是实现指导
- **复杂模块用子 BR 保留层级** — 如维修项目管理拆为"信息展示""操作交互""添加方式（手动/工单导入/报价单导入）"三个子 BR

### 操作流程视角（必须补充）

除了按功能模块拆分 REQ/BR，还必须从用户操作角度描述端到端流程：
- 每个核心功能必须有一个"用户操作步骤"描述（Step 1 → Step 2 → ... → 完成）
- 流程中的分支（成功/失败/异常）必须明确
- 这个操作流程是研发理解"用户从头到尾怎么用"的关键

### 流程图规则

- **系统行为 vs UI 提示必须区分** — 提示文案（如"如转译有误请联系总部"）不能作为流程节点
- **每个节点必须明确主语** — 是人工操作还是系统自动（如"系统提交照片给定损员"不是"人工拍照发给定损员"）
- 流程图画完后必须和 PRD 文本交叉验证每个节点

### GAP 标注规则

- **GAP = PRD 确实缺失的信息**，不是"我觉得应该有但 PRD 没写"
- 标 GAP 前必须先问：这个"缺失"是否有合理的设计原因？
- 不确定的推断标为 OPEN（待确认），不标为 GAP（确定缺失）
- **不是所有外部回传都需要对应系统状态** — 有些回传只是信息展示，不触发状态迁移
- **不要把正常的业务流程当缺口** — 如"定损金额和结算金额不一致"在汽车维修行业是常态

### 状态机完整性检查

- 状态机的**每条迁移边**都必须有对应的数据流定义（触发条件 + 回传数据 + 系统行为）
- 检查方法：遍历状态机每条边，确认 BR 中有对应描述
- **循环边（如驳回→重新发起）容易遗漏数据流定义**，必须单独检查
- **严格区分状态（节点）和事件/动作（边）** — "小米提交申请""保司提交定损"是迁移动作，不是状态节点，不能画成节点
- **正常路径和异常路径必须分开画** — 如"正常结案→正常赔付"和"异常终结→拒赔/零结/注销"是两条不同的路径
- **驳回循环的目标节点必须精确** — 看清箭头指向的是哪个状态，不能想当然
- **图片底部/边缘的注释文字不能遗漏** — 往往包含关键的补充规则

### 示例

```
REQ-001: 用户可以按条件筛选工单列表
  BR-001: 筛选项包含：待处理、处理中、已完成（parent: REQ-001）
  BR-002: 支持多选，默认全选（parent: REQ-001）
  BR-003: 筛选结果实时刷新，无需手动点击搜索（parent: REQ-001）
  SE-001: 空结果时展示"暂无数据"提示（mapped: REQ-001）
  SE-002: 筛选条件在页面刷新后保持（mapped: REQ-001）
  SE-003: 筛选不影响列表排序规则（mapped: REQ-001）
  GAP-001: PRD 未定义多个筛选条件的组合逻辑（AND/OR）（related: BR-001, BR-002）
```

## 执行流程

**严格按顺序执行，不得跳步：**

```
Step 0: 证据采集（文档抓取+图片下载）
Step 1: 图片全量解析（逐张描述语义，输出图片资产表）
Step 2: 通读全文+图片，建立完整业务理解（识别核心流程、状态机、角色关系）
Step 3: 需求结构化（REQ/BR/SE/GAP/OPEN）
Step 4: 自检（逐项对照 gate checklist，diff 旧版产物）
Step 5: Judge/Critique（切换到批评者视角审视自己的输出）
Step 6: 修正（根据 Judge/Critique 发现的问题修正报告）
→ 全部通过后才能 finalize
```

### Step 0: 证据采集（图片必须先行）

**飞书直读：**

```bash
python3 scripts/feishu_direct_ingest.py "<feishu_url>" -o output/<id>/phaseA --save-raw-blocks
```

**图片语义解析（P0 必做，不是可选）：**

下载完成后，必须先完成所有图片的语义解析，再开始写报告。

```bash
python3 scripts/parse_image_assets.py \
  --manifest output/<id>/phaseA/asset_manifest.json \
  --output-json output/<id>/phaseA/image_semantics.json \
  --output-md output/<id>/phaseA/image_semantics.md \
  --details-dir output/<id>/phaseA/image_details \
  --backend auto
```

如果自动解析不可用，必须逐张读取图片并记录语义描述。每张图片必须输出：
- 文件名
- 语义描述（这张图是什么）
- 关联的 REQ/BR（这张图对应哪个需求点）

**状态机图、流程图、泳道图是 P0 必解析项** — 必须转为 Mermaid 输出到报告中。如果无法解析，标为 GAP P0 阻断。

可选文档摘要预处理（降低后续 Phase token 消耗）：

```bash
python3 scripts/summarize_text.py \
  --input output/<id>/phaseA/plain_text.txt \
  --output-md output/<id>/phaseA/plain_text_summary.md \
  --output-json output/<id>/phaseA/plain_text_summary.json
```

图片未解析时，结论标记 `NEEDS_CONTEXT`，关键语义进入 `GAP/OPEN`。

### Step 1: 图片全量解析

在写报告之前，必须先完成所有图片的语义解析。

1. 逐张读取所有下载的图片（board 类优先，通常包含流程图/状态机）。
2. 每张图片记录：文件名、语义描述、关联的业务模块。
3. 状态机图 → 转为 Mermaid `stateDiagram-v2`。
4. 流程图/泳道图 → 转为 Mermaid `flowchart`。
5. 输出图片资产表到报告中（文件名 | 语义描述 | 关联 REQ）。
6. 如果图片无法解析，标为 GAP P0 阻断。

**Step 1 即时检查（图片解析完成后立即执行）：**
- [ ] 状态机图是否转为 Mermaid？节点是否只有状态（名词），动作在边上？
- [ ] 流程图中是否有 UI 提示被当作流程节点？
- [ ] 图片底部/边缘的注释文字是否遗漏？
- [ ] 正常路径和异常终结是否分开画？

### Step 2: 通读全文+图片，建立完整业务理解

1. 通读 PRD 全文 + Step 1 解析的图片语义，建立完整的业务理解。
2. 识别核心要素：业务流程、状态机、角色权限、系统边界、数据流向。
3. 标注 PRD 中的模糊点、矛盾点、缺失点（后续进入 GAP/OPEN）。
4. 如果是重跑，必须先读取旧版产物（`phase_a_report.md` + `phase_a_structured.json`），新版必须是旧版的超集。

### Step 3: 需求结构化 (REQ/BR/SE/GAP/OPEN)

#### 3a. 需求点与分支需求 (REQ/BR)

1. 逐段提取 REQ（功能点级别）。
2. 拆分分支需求为 BR（验收条件级别，必须包含完整字段、枚举值、校验规则、提示文案）。
3. 对每条需求补齐非功能语义（幂等/一致性/权限/可观测性）并落到 SE。

**3a 即时检查（写完 REQ/BR 后立即执行）：**
- [ ] 抽查任意一个 BR：是否只有概括描述？→ 有则返工，补充具体字段
- [ ] 最复杂的 REQ：BR 是否保留了 PRD 层级结构？→ 压平则返工
- [ ] 是否有操作流程描述？→ 至少核心功能有 Step1→Step2→完成
- [ ] PRD 中出现"并发""同时""批量"关键词时：是否提取了幂等/并发 SE 或 GAP？

#### 3b. 关键语义显式化 (SE)

1. 从文本与图片共同抽取 SE，禁止隐含语义。
2. 每个 SE 必须绑定到 REQ/BR。
3. 每个 SE 必须具备可验证判定依据（筛选层级、状态谓词、排序键、去重键等）。

**3b 即时检查（写完 SE 后立即执行）：**
- [ ] 每个 SE 是否有判定依据列？→ 必须是表格格式，不是纯文字
- [ ] 状态机的每条迁移边是否都有对应 SE？→ 遍历边，逐条确认
- [ ] 循环边（如驳回→重新发起）是否有数据流定义？→ 容易遗漏

#### 3c. 缺口与待确认 (GAP/OPEN)

1. GAP：PRD 存在实现依赖但无明确口径。每个 GAP 必须标注风险等级（P0/P1/P2）。
2. OPEN：口径冲突/多解，需要评审拍板。每个 OPEN 必须标注决策方。
3. 每个 GAP/OPEN 必须挂载到具体 REQ/BR/SE，禁止孤立条目。
4. 每个异常流场景必须标明由 PRD 哪句话推导，无法标明视为低置信度。

**3c 即时检查（写完 GAP/OPEN 后立即执行）：**
- [ ] 每个 GAP 是否有风险等级（P0/P1/P2）？
- [ ] 每个 OPEN 是否有决策方（产品/研发/业务）？
- [ ] 对每个 GAP 问：这个"缺失"是否有合理的设计原因？→ 有则改为 OPEN 或删除

### Step 4: 自检（提交前强制检查）

**写完报告后，必须逐项对照以下清单自检，全部通过才能进入 Step 5：**

- [ ] 每条 PRD 中的明确需求都已进入 REQ/BR
- [ ] 每个 BR 包含完整的字段列表、枚举值、校验规则、提示文案（禁止概括性描述）
- [ ] 每条关键语义都已进入 SE，且有判定依据
- [ ] 每个冲突点都已进入 OPEN（含决策方）
- [ ] 每个缺失口径都已进入 GAP（含风险等级 P0/P1/P2）
- [ ] 每张图片都有语义描述和关联 REQ
- [ ] 状态机已转为 Mermaid 图
- [ ] 流程图已转为 Mermaid 图
- [ ] 未输出 UT/EUT
- [ ] 如果是重跑：新版是旧版的超集（REQ/BR/SE/GAP/OPEN 数量不减少，内容不丢失）

### Step 5: Judge/Critique（提交前自我评审）

**自检通过后，切换到批评者视角审视自己的输出：**

1. **Judge 评审**：对照 PRD 原文逐条验证每个 REQ/BR/SE 的准确性。
   - 每个 BR 能否在 PRD 中找到原文依据？
   - 每个 SE 的判定依据是否具体可测试？
   - GAP/OPEN 是否遗漏了 PRD 中的模糊点？
   - 图片中的业务规则是否全部提取？

2. **Critique 批评**：假设输出有遗漏和错误，主动找问题。
   - 重点检查：并发/幂等/权限/异常流/状态迁移边界
   - 对照已知 bug 案例模式（从 `_upstream_context.md` 中的 BUG_CASES 章节获取）
   - 每个发现记录为：问题类型（FN/FP/VAGUE）+ 严重度 + 修正建议

3. 将 Judge/Critique 发现的问题记录在报告末尾的"自我评审记录"章节。

### Step 6: 修正

根据 Step 5 发现的问题修正报告：
1. 补充遗漏的 BR/SE/GAP/OPEN。
2. 细化概括性描述为具体字段和规则。
3. 修正不准确的判定。
4. 修正完成后，重新执行 Step 4 自检确认。

**全部通过后，才能执行 `dqg-run <project> finalize A`。**

## 上下文加载与缓存原则（Token 优化，严格执行）

### 缓存优先，禁止重复读取

| 缓存文件 | 存在时 | 不存在时 |
|----------|--------|---------|
| `_upstream_context.md` | 直接用，不回读 PRD 原文 | 由 context_loader 自动生成 |
| `image_semantics.md` | 直接引用文本，不重新读图片 | Step 1 中逐张解析后生成 |
| `plain_text_summary.md` | 用摘要代替全文 | PRD >3000 行时执行摘要预处理 |
| `phase_a_structured.json`（重跑） | 先读取作为基线，增量修改 | 首次执行正常生成 |
| `_prev_counts.json` | finalize 时自动对比 | finalize 时自动生成 |

### 禁止浪费 token 的行为

1. 禁止在 `image_semantics.md` 已存在时重新逐张读取图片
2. 禁止在 `_upstream_context.md` 已存在时回读飞书原文或 `plain_text.txt`
3. 禁止重跑时不读旧版产物从零开始
4. 禁止对同一张图片读取两次

### 图片语义规则

1. **图片中的业务规则必须提取到 SE/GAP/OPEN，不能跳过。**
2. **状态机图、流程图、泳道图是 P0 必解析项** — 漏掉等于漏掉需求骨架。
3. **无法解析的图片必须标为 GAP P0 阻断**，禁止标记 NEEDS_CONTEXT 后跳过。
4. 状态机图必须转为 Mermaid `stateDiagram-v2`，流程图转为 Mermaid `flowchart`。
5. 解析完成后必须输出 `image_semantics.md` 作为缓存。
