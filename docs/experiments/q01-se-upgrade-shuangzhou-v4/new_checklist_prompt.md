## SE 推导 Checklist（逐维度扫描）

对每个 REQ/BR，按以下维度逐一检查，有发现则生成 SE：

### 状态机完整性
- 每条迁移边是否有触发条件和数据流定义？
- 是否存在非法跳转路径？如何拦截？
- 终态是否不可回退？
- 循环边（驳回→重新发起）的数据流是否定义？
- 并行状态（如审批中+发放中）是否互斥？

**示例对照（生成 SE 时必须参照下列写法强度）：**
- 场景：PRD 定义了 N 个状态，但未列出非法跳转
  - ✗ 不可验证写法：需要拦截非法状态跳转
  - ✓ 可验证 SE：除 PRD 明示的 K 条合法迁移外，其余任意 (src, dst) 调用必须返回 409 CONFLICT 且不修改状态
  - ✓ 判定依据：对每个非法 (src, dst) 组合发一次状态迁移请求；断言 HTTP 409 + errorCode=INVALID_TRANSITION + 查询状态未变
- 场景：同一 src 状态有多条出边（如发放失败→完成 / 发放失败→重新申请）
  - ✗ 不可验证写法：根据业务规则决定流向
  - ✓ 可验证 SE：发放失败后，若 retry_count < 3 流转到待提交；否则流转到完成并打终态标记
  - ✓ 判定依据：参数化测试：retry_count ∈ {0, 2, 3, 5}，断言目标状态分别为 {待提交, 待提交, 完成, 完成}

### 并发/幂等
- 同一资源被多人同时操作时的行为？（乐观锁/悲观锁/队列）
- 重复提交同一请求的结果？（幂等键是什么？）
- 批量操作中部分失败时的回滚策略？

**示例对照（生成 SE 时必须参照下列写法强度）：**
- 场景：多用户同时对同一业务对象（VIN/订单号/工单 ID）执行写操作
  - ✗ 不可验证写法：需要并发控制防止重复提交
  - ✓ 可验证 SE：同一 {业务主键} 并发发起 N 次写操作时仅允许 1 次成功，其余返回 409 CONFLICT + errorCode=DUPLICATE_SUBMIT，数据库仅产生 1 条记录
  - ✓ 判定依据：CountDownLatch 发起 N 个并发请求；断言恰好 1 次 2xx、N-1 次 409；SELECT COUNT(*) WHERE {业务主键}={x} 结果为 1
- 场景：客户端重试同一请求（网络抖动/超时重发）
  - ✗ 不可验证写法：防止重复数据
  - ✓ 可验证 SE：相同 idempotencyKey + 相同 payload 的请求在 {时间窗口} 内必须返回首次结果，不触发二次业务逻辑
  - ✓ 判定依据：先调用成功获取 responseA；立即重放同 payload+idempotencyKey 获取 responseB；断言 responseA==responseB 且下游（订单/支付）仅被调用 1 次

### 异常恢复
- 中间步骤失败时的回滚/补偿策略？
- 失败后能否重试？重试是否幂等？
- 异常状态的数据是否会被后续流程误读？

### DDD 聚合边界
- 核心业务对象的聚合根是什么？聚合边界在哪？
- 跨聚合的操作是否通过领域事件解耦？
- 聚合内的不变量（invariant）是否在领域层校验？

**规则**：每个维度至少扫描一遍。无发现时跳过，不要强行生成 SE。
有发现时，SE 必须绑定到具体 REQ/BR，且有可验证的判定依据。
**写法强度**：生成的 SE 描述和判定依据必须达到上述 ✓ 示例的具体化程度，仅凭描述可直接写出单测。
