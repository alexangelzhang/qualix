# DQG Phase & Step 速查表

> 全流程 6 个 Phase，约 55 个 Step。每个 Phase 末尾有统一的"自检 → Judge/Critique → 修正"三步闭环。

## 流程总览

```
Q01 需求结构化（起点）
 ├── Q03 技术方案质量评审（可与 Q04 并行）
 ├── Q04 技术方案覆盖度审计（可与 Q03 并行）
 ├── Q05 单测生成
 ├── Q06 单测覆盖审计
 └── Q07 代码评审
```

---

## Phase Q01: 需求结构化

| Step | 名称 | 说明 |
|------|------|------|
| 0 | 证据采集 | 文档抓取 + 图片下载 |
| 0.5 | 假设前置 | 列出所有假设，等用户确认后再继续 |
| 1 | 图片全量解析 | 逐张描述语义，输出图片资产表 |
| 2 | 通读全文+图片 | 建立完整业务理解（核心流程、状态机、角色关系） |
| 3 | 需求结构化 | REQ/BR/SE/GAP/OPEN 提取 |
| 4 | 自检 | 逐项对照 gate checklist |
| 5 | Judge/Critique | 切换到批评者视角审视输出 |
| 6 | 修正 | 根据 Step 5 发现的问题修正报告 |

**产出**: `phase_a_report.md`, `phase_a_structured.json`
**放行**: REQ/BR 结构化率 100%, SE 显式化率 100%

## Phase Q03: 技术方案质量评审

| Step | 名称 | 说明 |
|------|------|------|
| 0 | 范围确认与链路梳理 | 确认评审范围，梳理 DDD+TMF 完整调用链路 |
| 1 | 架构设计评审 | 分层合理性、职责划分 |
| 2 | 接口设计评审 | API 契约、参数校验 |
| 3 | 数据模型评审 | 表结构、字段设计 |
| 4 | 异常与容错评审 | 异常处理、降级策略 |
| 5 | 性能与可观测性评审 | 性能瓶颈、监控埋点 |
| 6 | Failure Mode 分析 | 故障模式与影响分析 |
| 7 | 完整性 Gate | 检查是否有遗漏维度 |
| 8 | 自检 | 逐项对照 gate checklist |
| 9 | Judge/Critique | 切换到批评者视角审视输出 |
| 10 | 修正 | 根据 Step 9 发现的问题修正 |

**产出**: `tech_design_quality_review.md`（含 CALL_CHAIN 章节）

## Phase Q04: 技术方案覆盖度审计

| Step | 名称 | 说明 |
|------|------|------|
| 0 | 输入准备与范围确认 | 重跑时必须先读取旧版产物 |
| 0.5 | [可选] 技术方案生成 | 无现成技术方案时，基于 Q01 产物 + 知识库自动生成 |

| 2 | BR 级覆盖详查 | 每个 BR 的技术实现细节 |
| 3 | SE 覆盖审计 | 语义级覆盖检查 |
| 4 | GAP/OPEN 闭环检查 | Q01 遗留问题是否已闭环 |
| 5 | 反向审计 | NEW_DESIGN + NOT_IN_SCOPE 检查 |
| 6 | 自检 | 逐项对照 gate checklist |
| 7 | Judge/Critique | 切换到批评者视角审视输出 |
| 8 | 修正 | 根据 Step 7 发现的问题修正 |

**产出**: `tech_design_coverage_review.md`
**放行**: REQ 覆盖率 100%, SE 覆盖率 >= 90%, GAP 闭环率 >= 60%

## Phase Q05: 单测生成

| Step | 名称 | 说明 |
|------|------|------|
| 0 | 输入确认与上下文加载 | 读取 Q01 产物 + 代码仓库 |
| 0.5 | 目标模块确定 | 三层驱动（Q01 产物 + 代码仓库 + 用户指定），不可跳过 |
| 1 | 单测设计 | EUT 矩阵 + 分支逻辑扫描，输出结构化 JSON |
| 2 | 架构上下文代码脚手架生成 | DDD+TMF 脚手架 |
| 3 | 单测强断言约束代码实现 | MockedStatic\<TMF\> 模式，禁止空洞 assertThrows |
| 3.5 | 多仓库完整性自检 | BLOCKED gate，任何仓库有 MISSING TC 则不能进入 Step 4 |
| 4 | 自检 | 逐项对照 gate checklist |
| 5 | Judge/Critique | 切换到批评者视角审视输出 |
| 6 | 修正 | 根据 Step 5 发现的问题修正 |

**产出**: `eut_matrix.md`, `temp/*DqgTest.java`
**放行**: EUT 覆盖所有 REQ/BR/SE, 强断言, 异常路径有测试

## Phase Q06: 单测覆盖审计

| Step | 名称 | 说明 |
|------|------|------|
| 0 | 基线、架构与范围确认 | 改动清单、影响模块、涉及层 |
| 1 | 需求场景建模 | 先于代码，从需求出发建模 |
| 1.1 | 关键语义（SEM）专项建模 | 语义级场景补充 |
| 2 | 场景 → 代码 → 测试映射 | 三层映射关系建立 |
| 3 | 分层职责一致性专项审计 | DDD + TMF 层级职责检查 |
| 4 | 异常分支专项审计 | Java 异常处理路径 |
| 5 | 异常分支强制断言审计 | 检查空洞 assertThrows |
| 6 | 覆盖率门禁与特殊规则检查 | JaCoCo 覆盖率 + 特殊规则 |
| 7 | Mapper/Service 断言 checklist 审计 | 逐层填写 checklist |
| 7.5 | 变异测试 | 默认开启，Step 6 全绿后自动触发 |
| 8 | 审计结论与风险分级 | PASS / PASS_WITH_RISKS / FAIL |
| 9 | 自检 | 逐项对照 gate checklist |
| 10 | Judge/Critique | 切换到批评者视角审视输出 |
| 11 | 修正 | 根据 Step 10 发现的问题修正 |

**产出**: `ut_audit_report.md`（按模块分章节）
**放行**: T1 核心异常分支有覆盖, 无 WRONG_TARGET

## Phase Q07: 代码评审

| Step | 名称 | 说明 |
|------|------|------|
| 1 | 找到 API Provider 入口 | 定位评审起点 |
| 2 | 追踪 CmdExe 编排逻辑 | 命令执行器的编排流程 |
| 3 | 进入 DomainService | 看 TMF.execute 的 decideSteps |
| 4 | 逐个 Step 检查 | Ability 和 Extension 的调用关系 |
| 5 | Extension 具体实现 | 实现逻辑 + Gateway 层 SQL |
| 6 | 标注保护点 | 在完整链路上标注分布式锁/幂等/状态校验 |
| 7 | 多入口保护检查 | 所有入口是否都经过保护点 |

**产出**: `review_report.md`（含调用链路图，每条发现标注链路位置）
**放行**: 无 BLOCKER, REQ/BR/SEM → CODE/TEST 覆盖缺口已确认
