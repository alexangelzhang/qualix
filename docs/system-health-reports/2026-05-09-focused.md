## 一、整体判断

三周数据给出的信号非常清晰：**Qualix 的失败不是"模型乱来"，是上下游的契约没对齐**。

- **Q01**（需求解析）失败 92 条。核心问题：示例文档与 schema 正则自相矛盾，模型按示例写、schema 拒收。
- **Q05**（单测场景生成）失败 225 条。核心问题分两层——七类结构合规问题（validator 能兜底，其中 1 类已止住），以及一类"形式合规但抓不到 bug"的范式级问题。
- **Q06**（单测覆盖审计）失败 352 条。核心问题：凭空审计 Q05 没产出过的 EUT 编号 76 条，加上 findings schema 缺字段 46 条。

**三个 Phase 合起来 669 条失败，占三周总量的 33%；但解决方案都不贵**——Q01 一份 schema 修正 + Q06 一条子集约束 + Q05 五个 validator + 一次生成范式改造。三周 P0 做完，预计砍掉这三个 Phase 80% 以上的失败。

**一句话结论：Q01/Q05/Q06 的失败不是模型能力问题，是契约工程问题。上下游对齐了，失败就消失了。**

## 二、Q01：示例与约束的"两张皮"

### 2.1 核心问题

Q01 的 92 条失败里，最显眼的是"需求 ID 正则不匹配"（28 条）。模式如下：

- **Skill 示例**里写 `BR-004-02`（带二级编号，表示"BR-004 的第 2 条子项"）
- **Schema 正则**只允许 `^(REQ|BR)-\d+$`（不带二级编号）
- **模型**照着示例生成了 `BR-004-02`，提交时被 schema 拒

**规则和约束分别在两个地方，模型只看到一半。** 更糟的是剩下的 64 条失败类型——bitable 表格解析错乱，多维表格的分层结构被扁平化成单行，需求子项全部丢失。这同样是契约问题：skill 没说清"遇到多维表格要递归展开"，schema 也没对"子项必须独立记录"做硬约束。

### 2.2 解法

**一条 P0 + 一条 P1，两周收工：**

- **P0·T1（0.5 周）**：修 Q01 skill 示例与 schema 正则的不一致——要么 schema 放宽允许二级编号 `^(REQ|BR)-\d+(-\d+)?$`，要么示例去掉二级编号。这是纯文档修正，无代码改动。
- **P1·T2（1 周）**：bitable 解析规则进 Q01 skill 必读 context——规定"多维表格每一行对应一条独立需求，嵌套子表需递归展开到独立 BR-ID"；schema 对"子项需求必须独立 `parent_id` 回链"加硬约束。

### 2.3 预期收益

Q01 的 92 条失败 → 预计压到 ≤10 条。Q01 不是重灾区，但它是全流程上游——Q01 产物的质量直接影响 Q03/Q05/Q06 的下游。**修好 Q01 等于给后面所有 Phase 省掉一层脏数据来源。**

## 三、Q05：两类问题一张图，一个已解一个待攻关

### 3.1 Q05 的 225 条失败其实分两层

这是整份报告最值得拆开讲的部分。Q05 的失败看起来有 7 类，但按"治理杠杆"重新切，其实只有两层：

| 层级 | 类型 | 案例数 | 治理方式 | 当前状态 |
|------|------|-------|----------|----------|
| **结构合规层** | weak-assert | 69 | weak_assert validator | ✅ 已止血 |
| 结构合规层 | mock-wrong | 42 | 反射校验 mock 返回类型 | ❌ 未落地 |
| 结构合规层 | mock-phantom-method | 35 | 反射校验 mock 方法存在 | ❌ 未落地 |
| 结构合规层 | eut-missing-se | 28 | 非空校验 se_id | ❌ 未落地 |
| 结构合规层 | wrong-directory | 18 | 路径模板校验 | ❌ 未落地 |
| 结构合规层 | compile-fail | 11 | 轻量编译门 | ❌ 未落地 |
| **有效性层** | **no-exception-test** | **22** | **生成范式改造** | ❌ **validator 拦不住** |

**六类结构合规问题 validator 可以兜底，一类有效性问题 validator 拦不住——这是 Q05 的命门。**

### 3.2 结构合规层：照抄 weak_assert 成功样本

Q05 的 weak_assert 是三周里**唯一走完"发现 → 归类 → 固化 → 止血"全流程的成功样本**：

1. 失败案例自动采集到 `regression/failure-library/phaseB/`
2. `_data_patterns.md` 归纳为 `SEED-phaseB-weak-assert-001`
3. 04-28 新增 `weak_assert` validator 挂进 Phase Gate
4. 同日铁律写进 CLAUDE.md：then 必须有具体断言方法和期望值
5. 新发量从每周 20 余条降到个位数

剩下五类（mock-wrong / mock-phantom-method / eut-missing-se / wrong-directory / compile-fail）**完全可以照这个模式照抄一遍**，技术难度远低于第一次。这就是第五章的 **P0·T5（2 周）**。

### 3.3 有效性层：validator 拦不住，必须改生成范式

no-exception-test 22 条的本质是：**业务方法明显有异常分支（throws 或 try-catch），Q05 只写 happy path，一条异常场景都不生成**。

这类 validator 为什么拦不住？因为产出在字段层面完全合规——EUT 结构齐全、se_id 回链正确、断言具体、路径正确。validator 看不出有什么问题。**问题在于"没生成的 EUT"而不是"生成的 EUT"——这是覆盖度问题，不是字段质量问题。**

更深一层看，模型默认的生成范式是：

> **一个 SE → 一条测试方法 → 一个 happy path 断言**

而真实代码里，一个业务方法往往对应 3-5 条分支——happy / 边界 / 异常 / 并发。模型产出的测试"跑得通 + 结构完整 + 断言具体"，但只覆盖一条分支。**生产环境上线后，测试全绿，bug 照样发生。**

要跨过这道坎，需要三层业务判断：

1. **分支枚举**：这个方法有哪些分支？（读 AST 可以做到）
2. **业务后果映射**：每个分支对应什么业务后果？（读需求文档可以做到）
3. **断言对准业务后果**：断言指向业务结果而非方法返回（`assertEquals(OrderStatus.PAID, order.status)` 而不是 `assertTrue(result)`）

**这三层中，第三层最关键也最难**——它需要"判断什么才是业务真正关心的后果"，这是领域知识。

### 3.4 解法：T5 + T6 组合拳

- **P0·T5（2 周）**：补齐五个 validator，结构合规层失败归零。这部分是"水到渠成"的工程工作。
- **P1·T6（3 周）**：Q05 skill 重写为三步流程——
  - 步骤 A：喂 AST 给模型，让它先列分支清单（happy / 边界 / 异常 / 并发）
  - 步骤 B：逐分支映射业务后果（返回值 / 状态变化 / 副作用），强制从需求文档取值
  - 步骤 C：基于 A+B 生成 EUT，断言字段通过 ID 回链到 B 的 business_outcome
  - 配套 PhaseGuardrail 加分支覆盖率校验：AST 列 5 条分支但 EUT 只覆盖 2 条即 WARN；关键方法（含 throws 或 try-catch）必须 ≥1 条异常分支 EUT 否则 BLOCKED
- **P2·T12（2 周）**：Q05 生产 bug 回归实验——挑 3 个项目各 10 条历史 bug，让 Q05 基于 bug 对应的需求重跑，看生成的 EUT 能否复现 bug。**这是对"Q05 是否真的有用"的终极验证。**

### 3.5 Q05 预期收益

按三档时间点：

| 指标 | 当前 | +4 周（T5 完成） | +8 周（T6 完成） | +12 周（T12 完成） |
|------|------|-----------------|-----------------|-------------------|
| 结构合规 6 类失败 | 156 | ≤20 | ≤5 | ≤5 |
| no-exception-test | 22 | 22 | 0 | 0 |
| EUT 抓 bug 能力 | 未观测 | 未观测 | 未观测 | ≥40% |

**12 周末的止损线：若 Q05 EUT 抓 bug 能力 <20%，说明 Q05 不适合靠生成式单测解决，需要转型（比如转向属性测试 / 变异测试路线）。**

## 四、Q06：一条子集约束 + 一份 schema，两周了结

### 4.1 核心问题

Q06 的 352 条失败，两个根因吃掉了绝大部分：

**① Phantom EUT：76 条（21.6%）**

Q06 审计了 Q05 根本没产出过的 EUT 编号——EUT-000、EUT-098、EUT-099 这类。模型不是从 Q05 产物里读 EUT ID，**是按测试代码"推理"EUT 编号**。每个 phantom EUT 都会让下游的 RSM 覆盖率对账失效。

**② findings 缺字段：46 条（13.1%）**

新发于 05-06（workflow-approval-demo 项目）。findings 的 id、severity 整段缺失。根因很简单——**schema 文档 `phase_c_structured.schema.json` 至今不存在**。Q06 skill 说了 findings 是 required，但没人能告诉模型每条 finding 要填哪些字段，结果模型按语感给了最少的两三个字段。

### 4.2 解法

两项 P0 任务，各 0.5 周：

**P0·T2（0.5 周）**：补 `phase_c_structured.schema.json`，把 findings 的 id / severity / message / target_eut / confidence 等字段必填清单同步到 Q06 skill prompt 开头。**这是纯文档工作**，照搬 Q05 的 weak_assert validator 套路即可。

**P0·T3（0.5 周）**：Q06 新增跨 Phase 硬约束——`validate_eut_id_subset`：Q06 产出的每个 eut_id 必须出现在 Q05 产物的 eut_id 集合里，不匹配即 BLOCKED。实现位置 `src/qualix/quality/checks/cross_phase_check.py`。**这是 76 条 phantom EUT 的唯一根治方案。**

### 4.3 预期收益

- T2 完成：workflow-approval-demo 重跑，0 条 findings 缺字段失败
- T3 完成：expense-approval-demo + workflow-approval-demo 重跑，phantom EUT 归零

Q06 的 352 条失败预计压到 ≤50 条。**这是整个项目性价比最高的两件事——一周投入，治理掉 300+ 条失败。**

## 五、三者的共同病根

把 Q01 / Q05 / Q06 放在一起看，三种不同的 Phase，**失败的深层原因完全一样——契约没对齐**：

| Phase | 失败形态 | 契约错配位置 |
|-------|---------|--------------|
| Q01 | ID 正则不匹配 28 条 | skill 示例 ≠ schema 正则 |
| Q05 | 6 类结构合规 156 条 | skill 要求 ≠ validator 覆盖 |
| Q05 | no-exception-test 22 条 | skill 范式 ≠ 测试真实目标 |
| Q06 | phantom EUT 76 条 | Q06 约束 ≠ Q05 产出 |
| Q06 | findings 缺字段 46 条 | schema required ≠ prompt 必填清单 |

**没有一条失败是"模型能力不够"——全部是"人类没把契约对齐"**。

这也解释了为什么补了三周 guard 失败量没下来：**guard 是拦截契约不一致的后果，不是解决契约不一致本身**。真正的投资回报在前置契约对齐，而不是后置拦截。

Q05 的 weak_assert 是唯一样本，证明"契约对齐 + validator 兜底"这套组合拳走通一次就能止血。剩下的活就是把这个样本复用到 Q01、Q06 和 Q05 的其余类型上。
