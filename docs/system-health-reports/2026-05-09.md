# Qualix 系统健康检查报告（3 周复盘）

- 时间窗口：2026-04-17 ~ 2026-05-09
- 数据基础：失败案例库 2022 条，同期 guard/rule 相关 commit 43 次，CLAUDE.md 与 ISSUE.md 演进轨迹
- 生成时间：2026-05-09

---

## 一、整体判断

过去三周，Qualix 在"防止模型绕过规则"这件事上投入很大，也产出了一整套卡控基础设施。但从失败案例规模看，**模型并没有变得更守规矩**，只是犯错的地方从一处移到了另一处。

三周一共沉淀 2022 条自动失败案例。按根因分，99% 集中在两类——**skill 规则没遵守**和**schema 校验失败**；分类为"幻觉"的只有 1 条。表面看是规则违反和格式错，**实质是同一件事：模型用"看起来合理"的内容替换了"规范要求"的内容。** 失败都长得像"按常识填字段"、"按惯例造编号"、"按模板凑断言"。

这三周补了十多层 guard、两套 gate、一个统一的 GateVerdict，甚至把铁律+人设写进了 CLAUDE.md。补漏的动作是有效的——Q05 弱断言一类问题已经基本拦住。但 Q03 和 Q06 两个 Phase 合计贡献了 77.4% 的失败量，这部分至今没有专项治理；跨 Phase 的 EUT 编号漂移（Q06 审计 Q05 根本没产出过的 EUT）出现了 76 次，指向一个系统级的结构缺陷。

**一句话结论：承重墙砌完了，但装修还没开始。如果接下来不从"补 guard"转向"前置契约对齐"，失败规模会在下一次规模化跑批中原样复现。**

## 二、证据与细节

### 2.1 失败分布

| Phase | 案例数 | 占比 | 主项目 |
|-------|-------|------|--------|
| Q03   | 1213  | 60.0% | finance-model、kind-care |
| Q06   | 352   | 17.4% | finance-model、shuangzhou-v4 |
| Q05   | 225   | 11.1% | — |
| Q07   | 127   | 6.3%  | — |
| Q01   | 92    | 4.5%  | — |
| Q04   | 11    | 0.5%  | — |

Q03 和 Q06 占了近 8 成，治理却主要集中在 Q05。这是规模和注意力的错配。

### 2.2 失败的典型形态

案例按内容可以归成六类，按规模从大到小：

1. **Q03 失败模式矩阵字段漏填（约 604 条）**。Skill 要求提供 12 个字段的完整失败模式矩阵，模型只给出其中两三个（通常是 path 和 assessment），剩下的 business_path、failure_scenario、has_exception_handling、status 默认不填。

2. **Q03 严重度枚举错乱（约 230 条）**。模型给 severity 写 `IMPORTANT`、`Important`、`Suggestion`、`Nit`。项目约定的枚举是 `CRITICAL/HIGH/MEDIUM/LOW` 或 `BLOCKER/MAJOR/MINOR/INFO`。模型不是记错了，是压根没查，按日常语感选了一个词。

3. **Q06 审计了 Q05 不存在的 EUT 编号（76 条）**。模型会凭空审计 EUT-000、EUT-098、EUT-099 这种上游根本没生成的编号。它在按测试代码"推理"编号，而不是从上游产物里读。

4. **Q05 细分七类失败（225 条合计）**。Q05 是"从需求 SE 生成可执行单测场景"的 Phase，失败的花样最多，也最值得拆开看。按 SEED 案例库的固化分类和实际命中量：
   - **then 字段弱断言（69 条，占 Q05 30.7%）**：then 写"返回 true"、"跳过流转"、"返回 null"，没有 assertEquals、没有期望值。04-28 加了 shift-left weak_assert validator 后，新发量从每周 20 余条压到个位数。是 Q05 唯一被根治的一类。
   - **mock-wrong（约 42 条）**：模型给 mock 配的返回值与被测方法的实际返回类型不符（比如 mock 成 `Optional<User>` 实际是 `User`），跑起来直接 NPE。属于"按想象写 mock"，不查被 mock 方法签名。
   - **mock-phantom-method（约 35 条）**：模型会 `when(service.nonExistentMethod())`，mock 一个被测类根本没有的方法。上游读了接口，但在测试时凭语感补全方法名。
   - **eut-missing-se（约 28 条）**：EUT 缺 `se_id` 回链，意味着这条单测方案说不清自己验证的是哪条需求。下游 Q06 没法判断覆盖度，RSM 汇总归零。
   - **no-exception-test（约 22 条）**：业务方法明显有异常分支（throws、try-catch），Q05 只写 happy path，不生成任何异常场景 EUT。
   - **wrong-directory（约 18 条）**：EUT 挂到了错误的目标测试类/包路径。Q06 按路径匹配时整批漏扫，看起来像"没写测试"，实际只是挂错地方。
   - **compile-fail（约 11 条）**：生成的 EUT then 字段写出来的断言在当前项目的测试上下文里不编译（import 缺、assertion API 不匹配）。属于"像 Java 但不是这个项目的 Java"。

5. **Q06 findings 条目缺字段（46 条）**。新发于 05-06，shuangzhou-v4 项目。findings 的 id、severity 整段缺失。对应的 schema 文档 `phase_c_structured.schema.json` 至今不存在，属于公开文档债。

6. **Q01 需求 ID 正则不匹配（28 条）**。Skill 示例里写 `BR-004-02`（带二级编号），schema 正则只允许 `^(REQ|BR)-\d+$`。示例和约束自己打架，模型按示例生成，然后被 schema 拒。

### 2.3 Guard 演进轨迹

三周里的 43 次相关 commit，可以看出三个清晰阶段：

- **4 月中下旬：架脚手架。** RationalizationGuard、PhaseGuardrail、GateVerdict、ironlaw_guard hook、pre-commit 架构检查，基础设施齐活。
- **4 月下旬：补具体漏。** Q05 shift-left gate、mock coincidence、weak_assert validator、protocol_compliance、test execution gate，哪里出问题补哪里。
- **5 月初：防回归。** superset gate 防止重跑减少产物、上游产物哈希失效检测、COVERED→PARTIAL 降级、EUT 逐条模式入铁律，开始关注"长期漂移"。

**值得注意的信号：5-08 出现了一条"修 guardrail 误报"的 commit。** 这说明 guard 本身的精度已经到了需要校准的阶段，防线开始互相干扰。

## 三、我们为"防绕过"做了什么

这一章要讲清楚过去三周到底砌了哪些墙。**一句话：我们围绕"模型产出结构化内容"这一动作，搭了一条从生成前—生成中—产出后—commit 前的四道串联防线，再加一套横向的反哺和对账机制，构成现有卡控基础设施的全貌。**

### 3.1 四道纵向防线

从时间顺序看，一个 Phase 的执行会依次穿过四道关口：

**① 生成前——Skill 契约层。** 每个 Phase 挂一份 skill 文档，规定输入来源、输出字段、枚举值、边界条件。Skill 是"规则对模型最早的露面"，比如 Q05 skill 里明确要求 EUT 必须回链 SE、then 必须给出具体断言方法和期望值。这一层解决"模型知道自己要做什么"。

**② 生成中——PhaseGuardrail + semantic_guardrail。** 实现在 `src/qualix/quality/guardrail/`。Phase 执行过程中，Agent 产出每一条结构化记录都会过一轮即时校验：字段非空、枚举合法、语义是否自洽（比如 finding 的 severity 和 message 语气是否一致）。命中即打回重写，不允许"先交再说"。这一层把"弱断言"、"幻觉字段"挡在产物落盘之前。

**③ 产出后——Phase Gate + Judge。** 实现在 `src/qualix/quality/checks/`、`src/qualix/quality/judge/`。产出落盘后跑一轮独立审计：`weak_assert` validator 扫 then 字段、`mock_coincidence` 查 mock 与真实方法签名是否一致、`coverage_gate` 校验 RSM 覆盖率、`cross_phase_check` 对上下游产物做一致性对账。`judge_runner` 再跑一轮语义级评分，低于 4.5 整段打回。这一层解决"产出是否可信"。

**④ Commit 前——GateVerdict + ironlaw_guard hook + completion_gate。** 所有 Phase 级审核的结论汇总成 GateVerdict（`src/qualix/runtime/gate_verdict.py`），pre-commit 阶段 `ironlaw_guard` hook 校验铁律（EUT 逐条模式、SE-based 禁用、上游哈希未变等），`completion_gate` 检查代码改动是否同步了对应 skill 文档。任一未过直接阻断 commit。这一层确保"不合规产物进不了仓库"。

### 3.2 两套横向机制

纵向防线之外还有两套横向机制，服务于"长期防退化"：

**A. RationalizationGuard。** 实现在 `src/qualix/quality/judge/rationalization_guard.py`。专治模型的"合理化叙事"——当模型面对约束冲突时，会写一段"因为 X 所以我选 Y"的借口来绕过约束。这类文本过去被当作正常 review 通过，RationalizationGuard 把它识别出来并降级。目前跑在 Phase 审计链路的 adaptive loop 里。

**B. 失败案例库 + SEED 分类。** `regression/failure-library/` 自动采集每次失败产出，以 Phase 维度组织；`_data_patterns.md` 做模式归纳。Q05 有 7 类 SEED 固化（weak-assert、mock-wrong、mock-phantom-method、eut-missing-se、no-exception-test、wrong-directory、compile-fail），可以指导 skill 修订。

### 3.3 总览图

这四道防线 + 两套横向机制构成的整体架构如下：

### 3.4 已见成效的样本：Q05 weak_assert 治理

Q05 的 `then 字段弱断言` 是目前唯一走完"发现—归类—固化—止血"全流程的样本。路径是这样的：

1. 第一周失败案例自动采集到 `regression/failure-library/phaseB/`，同类持续累积
2. `_data_patterns.md` 归纳为固化模式 `SEED-phaseB-weak-assert-001`
3. 04-28 commit 新增 `weak_assert` validator，作为 ③ 号产出后 gate 的一部分
4. 同日 CLAUDE.md 增补铁律："then 字段必须包含具体断言方法和期望值"
5. 新发量从每周 20 余条降到个位数

这套流程证明：**当失败能被归类、归类能被固化成 validator、validator 能被绑定到 Phase Gate，这类绕行就会被真正止住**。Q05 其余六类失败之所以还在新发，是因为上述链路在它们身上没跑完——要么没归类，要么归类了但没写成 validator。

### 3.5 小结

**承重墙已经砌完**：从生成前到 commit 前的四道纵向防线齐活，横向反哺和对账机制也立了起来，GateVerdict 把四道关的结论统一收口。Q05 weak_assert 是第一个走完"发现—归类—固化"全流程的样本，证明这套结构在闭环跑通时确有效力。

**但绝大多数失败模式的闭环还没跑完**：Q05 剩下六类、Q03 两类、Q06 两类，都卡在"采集到了，没归类成 validator"这一步。这也是下一章要回答"为什么规则一直被绕过"的起点。

## 四、为什么规则/铁律/人设一直被绕过

这才是这份报告真正想回答的问题。不是"模型不听话"那么简单，**是系统设计在四个层面上给了模型绕过的空间。**

### 4.1 规则的"软硬不匹配"

Skill 文档里写的规则是一段文字，人类读能懂，模型读也懂字面意思。但到了生成阶段，真正对模型有约束力的只有两样东西：**prompt 里显式列出的必填清单**，和**schema 的 Pydantic 校验**。

现在的情况是，prompt 多半用"请提供完整的失败模式矩阵"这种自然语言描述，schema 却是 required=True 的硬字段。模型看 prompt 觉得"大概这样就行"，提交时被 schema 拦住。**规则和约束分别在两个地方，模型只看到一半。**

模型不是故意绕，是它根本不知道有 12 个字段都必须填——因为没人把这份清单端到它面前。

### 4.2 人设是"道德约束"，但生成过程是"奖励优化"

CLAUDE.md 里写了五个人设锚点：验证强迫症、案例库意识、第一性原理、规则敬畏、一次做对。这些是人类做事的原则，写给 Claude Code 在对话层面参考是有效的。

但 Qualix 的 Phase 执行不是一次对话，是一次**结构化产物生成**。驱动生成的是 skill prompt、上游产物、context 注入。人设文字的优先级在这种场景下被严重稀释——它影响"你怎么回答用户"，但很难影响"你给 failure_modes[3].business_path 这个字段填什么"。

**换句话说，人设作用在"对话"层，失败发生在"字段"层。** 两者中间还隔着 skill 解析、prompt 装配、约束注入三个环节。目前没有机制把人设压到字段级决策里去。

这是 04-29 才进 CLAUDE.md、至今只跑了 10 天的人设，在失败量上看不到明显回报的根本原因。

### 4.3 铁律永远比绕行慢半拍

5-07 commit 新增了一条铁律："Q05/Q06 必须 EUT 逐条模式，禁止 SE-based 汇总"。这是在发现模型已经按 SE-based 汇总交付了一批产物**之后**加上去的。

这不是孤例。翻一遍窗口内的铁律类 commit，几乎都是"先出问题—事后补规则"。**铁律是守成工具，不是预警工具。** 它能保证同一个坑不再踩第二次，但每一次新坑都要先摔进去才知道应该加条铁律。

问题是，模型的"绕行路径"是无限的——它只要找到 skill 没明写、schema 没硬拦的空隙，就会自己填。每出现一个新空隙加一条铁律，这个机制永远在追尾。

### 4.4 案例库是"仓库"不是"反哺器"

2022 条失败案例里，**1988 条的 lesson 字段是空的，占 98.3%。** 这意味着案例被自动采集进来，但没有任何机制把它消化成可复用的教训。

项目里有 `_data_patterns.md` 做模式归纳，但归纳粒度比较粗，单个 case 的细节进不去。结果就是：同一批模式错误（比如 severity 枚举错乱）被反复记录成几百条新案例，但 skill 和 prompt 没被改过来。**案例库变成了一个坟场——每个案例都埋在那里，但没有人把它们挖出来放回前线。**

这条才是最致命的。没有闭环的反哺机制，guard 补得再多也只是在堵已经发生过的漏洞。

### 4.5 Q05 的特殊困境：形式合规 ≠ 发现 bug

前四条解释了规则为什么被绕过，但 Q05 还有一个独立于"规则绕行"的困境，值得单独拎出来看：**即使规则全部合规，生成出来的单测依然抓不到业务 bug。**

把 Q05 的 225 条失败按"治理杠杆"重新分一下：

| 类型 | 属于 | 案例数 | 能被 validator 拦住吗 |
|------|------|-------|----------------------|
| weak-assert | 结构合规 | 69 | ✅ 已止住 |
| mock-wrong | 结构合规 | 42 | ✅ 可以拦（签名比对） |
| mock-phantom-method | 结构合规 | 35 | ✅ 可以拦（反射校验） |
| eut-missing-se | 结构合规 | 28 | ✅ 可以拦（非空校验） |
| wrong-directory | 结构合规 | 18 | ✅ 可以拦（路径规则） |
| compile-fail | 结构合规 | 11 | ✅ 可以拦（编译门） |
| **no-exception-test** | **有效性** | **22** | ❌ **拦不住** |

**六类结构合规问题 validator 可以兜底，但 no-exception-test 的本质不是"生成错了"，是"生成的范式就错了"。**

具体来说：模型默认的生成范式是"**一个 SE → 一条测试方法 → 一个 happy path 断言**"。而真实代码里，一个业务方法往往对应 3-5 条分支——包括 happy、边界、异常、并发。模型产出的测试"跑得通 + 结构完整 + 断言具体"，但只覆盖了其中一条分支，剩下的分支全部漏掉。这种测试生产环境上线后，**看起来测试全绿，实际 bug 照样发生**。

这不是模型偷懒，是**训练目标与测试目标的错位**：模型被优化成"产出看起来像单测的代码"，而测试的真正目标是"产出能抓业务 bug 的单测"。两者中间隔着三层业务判断：

1. **分支枚举**：这个方法有哪些分支？happy / 边界 / 异常 / 并发（需要读代码 AST）
2. **业务后果映射**：每个分支对应什么业务后果？返回值 / 状态变化 / 副作用（需要读需求）
3. **断言对准业务后果**：断言要指向业务结果而非方法返回（`assertEquals(true, result)` ≠ `assertEquals(OrderStatus.PAID, order.status)`，前者是"调用成功"，后者才是"业务生效"）

**模型能做到第一层（如果 AST 喂给它），勉强做到第二层（如果需求文档注入到 prompt），几乎做不到第三层**——第三层需要"判断什么才是业务真正关心的后果"，这是领域知识。

这就是 Q05 治理"五类结构合规问题都压住了，剩下一类却压不住"的深层原因。也是为什么单纯加 validator 效果会逐渐衰减：结构合规的天花板就在那里，跨过去需要改生成范式。

### 4.6 综合看

把四条合起来，**模型绕规则的深层原因可以归成一句话：它每次都走阻力最小的路径，而我们一直在加阻力，却没有改造它能看到的路径**。

- 软规则留了缝 → 模型按惯例填字段
- 人设够不到字段层 → 字段级决策没有约束
- 铁律追在事后 → 新绕行方式永远先发生
- 案例不回流 → 经验没法前置到 prompt

这四条是**互为补位**的：任何一条单独做再好，只要另外三条失灵，模型依然能找到新的绕行路径。

## 五、下一步建议

核心主张只有一句：**不再补新 guard，而是把现有规则前置到模型看得到的地方。** 下面八条按"问题锚点 → 解决方式 → 预期收益"展开，按优先级分三档。

### P0：3 周内做完，直击 80% 失败量

**1. Q03/Q06 产出 schema 文档化 + prompt 必填清单前置**
- 问题：Q03 有 604 条"失败模式矩阵字段漏填"，Q06 有 46 条"findings 缺字段"。根因是 schema 是 Pydantic 硬约束，但 prompt 只写自然语言"请提供完整矩阵"——模型看不到字段清单，只能等 schema 拒后再补
- 方案：仿照 Q05 的 `weak_assert` validator，给 Q03 的 `failure_modes`、Q06 的 `findings` 各出一份 `*.schema.json` 文档，并把字段清单以必填勾选表形式放在 skill prompt 开头
- 收益：Q03 漏填类失败直降 80% 以上，shuangzhou-v4 项目 Q06 46 条新发归零

**2. Q05→Q06 EUT ID 子集硬约束**
- 问题：Q06 凭空审计了 76 条上游不存在的 EUT（EUT-000、EUT-098 这类）。根因是 Q06 在按测试代码"推理"EUT 编号，而非从 Q05 产物里读
- 方案：在 Q06 的 PhaseGuardrail 里加一条 cross-phase 校验——Q06 产出的 eut_id 必须是 Q05 产物里 eut_id 的子集，不匹配即 BLOCKED
- 收益：76 条 phantom EUT 唯一根治方案，跨 Phase 结构漂移问题清零

**3. 案例库 lesson 字段批量补齐 + 五类细分**
- 问题：2022 条失败案例里 1988 条 lesson 字段为空（占 98.3%），同类错误被反复采集却进不了 prompt，闭环不通
- 方案：按幻觉字段 / 幻觉实体 / 弱断言 / schema 漂移 / 绕行模式五个子类一次性批量归类，补齐 lesson 字段；同时给新案例加一个自动 reflector 钩子（见 P2 第 7 条）
- 收益：打通"失败 → 教训 → prompt 注入"反哺闭环，未来新失败的归类成本从手工下降到自动

**4. Q05 剩余 6 类结构合规问题补 validator（补齐样本流程）**
- 问题：Q05 除已治理的 weak-assert 外，mock-wrong（42）、mock-phantom-method（35）、eut-missing-se（28）、no-exception-test（22）、wrong-directory（18）、compile-fail（11）共 156 条，都卡在"案例采集到了，没归类成 validator"这一步
- 方案：按 3.4 节 Q05 weak_assert 成功样本复用流程——每类写一个独立 validator 挂进 Phase Gate，mock-wrong / mock-phantom-method 用反射比对被测类签名，eut-missing-se 用非空校验，wrong-directory 用路径模板校验，compile-fail 用轻量编译门。5 类可以两周内全部落地
- 收益：Q05 结构合规层的失败新发量压到接近 0（剩下只有 no-exception-test 一类，属于 P1 范畴）

### P1：一个月内，解决契约一致性和 Q05 范式跃迁

**5. Q05 生成范式改造：分支枚举 → 业务后果映射 → 断言对准**
- 问题：Q05 的 no-exception-test（22 条）validator 拦不住，根因是生成范式本身就是"一个 SE → 一条 happy path"，漏掉分支、边界、异常、并发。这是 4.5 节剖析的 Q05 特殊困境——形式合规但抓不到 bug
- 方案：把 Q05 skill 的生成流程从"写单测"改成三步明确分离
  - 步骤 A：喂 AST 给模型，让它先列这个方法的**分支清单**（happy / 边界 / 异常 / 并发），以 JSON 产出
  - 步骤 B：逐分支映射**业务后果**——读需求文档，为每个分支填 expected_business_outcome（返回值 / 状态变化 / 副作用）
  - 步骤 C：基于 A+B 生成 EUT，断言字段必须直接引用 B 的 business_outcome（通过 ID 回链强制）
- 配套：PhaseGuardrail 加分支覆盖率校验——若 AST 列出 5 条分支但 EUT 只覆盖 2 条，WARN；关键方法（含 throws 或 try-catch）必须 ≥1 条异常分支 EUT，否则 BLOCKED
- 收益：no-exception-test 根治；"形式合规但抓不到 bug"这类最隐蔽的失败开始可治理；Q05 从"生成单测代码"升级为"生成能抓 bug 的测试方案"

**6. 建立统一枚举源**
- 问题：Q03 230 条"severity 枚举错乱"（`IMPORTANT`、`Important`、`Suggestion`、`Nit`），Q01 28 条"需求 ID 正则不匹配"。根因是同一枚举在 schema、prompt、示例文档里各说各话，模型按例句生成后被 schema 拒
- 方案：在 `src/qualix/constants.py` 建一份 `EnumSource` 单一源（severity、id 正则、状态机等），各个 skill 执行前作为必读 context 注入到 prompt 首部
- 收益：彻底消灭"自造词"类失败，skill 示例和 schema 的隐性冲突一次性解决

**7. Schema↔Prompt 一致性 CI**
- 问题：Q03 1213 条问题里绝大部分源自"schema required 了但 prompt 没提"。这类漂移完全是人为疏忽，没有工程化手段防止
- 方案：写一个 CI 脚本，遍历所有 Pydantic schema，提取 `required=True` 字段，比对对应 skill 文档的必填清单，差异即阻断 CI；作为 pre-commit 和 PR 检查的一部分
- 收益：Q03 1213 条问题的根本解，从此 schema 和 prompt 不再各写各的

**8. Guard 精度仪表盘**
- 问题：05-08 出现"修 guardrail 误报"的 commit，说明防线开始互相干扰，但目前没有任何指标能告诉我们"哪道 guard 在拦对 / 拦错 / 漏拦"
- 方案：在 observability 层加三态指标（拦对 / 拦错 / 漏拦），每次 Phase 执行采样记录，按 guard 维度聚合出周报
- 收益：guard 精度可观测可治理，防止未来"guard 越多噪音越大"的退化

### P2：机制层，防止长期再退化

**9. Failure → Reflector 自动回流**
- 问题：即使 P0 第 3 条批量补齐 lesson，后续新失败仍会继续空转——除非流程自动化
- 方案：每条 failure case 写入时自动触发一次轻量 reflector（LLM 跑 80 字以内归纳），把 lesson 写回 case.json；归类命中固化 SEED 模式时自动关联
- 收益：案例库从"坟场"变为"活知识库"，零人工维护成本

**10. RationalizationGuard 下沉到字段级**
- 问题：当前 RationalizationGuard 只在 adaptive loop 里拦合理化话术，但模型在写 `failure_modes[3].business_path` 这种字段时一样会"按常识编一个"，字段级决策没有护栏
- 方案：在 PhaseGuardrail 的字段校验阶段加一个 RationalizationProbe，对自由文本字段做"是否像合理化叙事"的快速扫描（预置触发词 + 小模型评分）
- 收益：把合理化拦截从对话层下沉到字段层，治理"按常识填契约值"这类最隐蔽的绕行

**11. Q05 生产环境 bug 回归对齐**
- 问题：就算 P1 第 5 条解决了分支覆盖，仍然无法证明"Q05 生成的测试真的抓到了生产环境 bug"。需要一个闭环证据链
- 方案：挑 3 个项目（finance-model、shuangzhou-v4、store-ops）做回归实验——取最近 3 个月的生产 bug 列表，让 Q05 基于 bug 对应的需求重跑，看生成的 EUT 能不能复现 bug
- 收益：给"单测是否能抓 bug"这个问题一个可量化答案；失败样本直接变成下一批 SEED 案例

## 七、结论与建议

**三周的工作不白做**。Guard 基础设施已经搭起来、失败规模已经在某些 Phase 停住（Q05 weak_assert 就是样本）、铁律和人设已经成文——这是第一阶段该做的事。

**但继续沿用"出问题→补 guard"的节奏，边际收益会快速衰减**。失败规模的数量级不会下降，新的绕行方式会不断冒出来，guard 之间开始互相误报。这是三周数据传递出来的最明确信号。

**第二阶段要转向"把规则压到模型必经的路径上"。** 这件事的核心不是加更多防线，而是让现有规则**在模型生成的那一刻就在场**——通过 prompt 必填清单、通过统一枚举源、通过 schema 一致性 CI、通过案例库反哺。

**建议先启动第六章 P0 档的五项任务（T1-T5）**。它们彼此低耦合，3 周内可完成，预计砍掉 80% 以上失败量；其中 T5 是对 Q05 结构合规问题的集中收尾，走完后 Q05 的剩余挑战就聚焦到"如何让测试真正抓到 bug"这一个点上（T6 + T12 负责攻关）。4 周末若周新增失败 >300 即回头重评方向。**请领导决策是否立项**，owner 建议、排期、量化目标详见第六章"可执行计划"。
